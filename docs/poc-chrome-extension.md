> Status: **PASS**
>
> Official `google-chrome-stable` 150, OpenCLI 1.8.6, Browser Bridge extension
> 1.0.22, Xvfb, openbox and loopback-only x11vnc have been built and exercised

## 2. Architecture

```text
opencli daemon (127.0.0.1:19825)
                 ^
                 | WebSocket /ext
                 |
Google Chrome stable + force-installed OpenCLI extension
                 ^
                 | Chrome managed extension update
                 |
CRX HTTP server (127.0.0.1:18181)
  - /updates.xml
  - /extension.crx

Xvfb :99 -> openbox -> Chrome headed window
       |
       +-> x11vnc (127.0.0.1:5900 and [::1]:5900)
```

The entrypoint starts components in this order:

```text
OpenCLI daemon -> Xvfb -> openbox -> x11vnc -> CRX HTTP server -> Chrome
```

Shutdown runs in reverse order under `tini` and a shell trap.

## 3. Why managed CRX installation is required

Chrome 150 stable rejects command-line unpacked extension loading:

```text
--load-extension is not allowed in Google Chrome, ignoring.
```

Therefore the image does not rely on `--load-extension` for normal operation.
Instead it:

1. verifies and unpacks the pinned release ZIP;
2. invokes Chrome's own `--pack-extension` command at image build time;
3. derives the Chrome extension ID from the fixed PEM public key using the
   required hexadecimal-nibble to `a`-through-`p` mapping;
4. generates an Omaha update manifest;
5. writes Linux managed policies under `/etc/opt/chrome/policies/managed`;
6. serves the CRX and update manifest from container loopback before Chrome
   starts.

Policy shape:

```json
{
  "ExtensionInstallForcelist": [
    "lieajjjjjggpnhebbjmmlfofjojallpe;http://127.0.0.1:18181/updates.xml"
  ],
  "ExtensionSettings": {
    "lieajjjjjggpnhebbjmmlfofjojallpe": {
      "installation_mode": "force_installed",
      "update_url": "http://127.0.0.1:18181/updates.xml",
      "override_update_url": true
    }
  }
}
```

Two implementation details were necessary for Chrome to install the extension:

- the CRX must be generated by a conforming CRX3 packer; the PoC delegates this
  to `google-chrome-stable --pack-extension` instead of hand-writing CRX3;
- Chrome must not start with `--disable-background-networking` or
  `--disable-component-update`, because those flags suppress the first managed
  extension update/install check.

## 4. Build

From the F1 workspace or repository root containing these files:

```bash
PROXY=http://127.0.0.1:7890

docker build \
  --network=host \
  --progress=plain \
  --build-arg HTTP_PROXY="$PROXY" \
  --build-arg HTTPS_PROXY="$PROXY" \
  --build-arg http_proxy="$PROXY" \
  --build-arg https_proxy="$PROXY" \
  -t opencli-hub:poc \
  .
```

The proxy arguments are only required when the build environment needs them.
The image performs all downloads at build time; runtime does not download
Chrome, OpenCLI, the extension or adapters.

## 5. Run with Chrome sandbox enabled

On the verified Docker host, the default seccomp profile blocks Chrome's user
namespace setup. The following keeps Chrome's sandbox enabled while relaxing the
container seccomp profile:

```bash
docker volume create opencli-hub-poc-data

docker run -d \
  --name opencli-hub-poc \
  --shm-size=2g \
  --security-opt seccomp=unconfined \
  -e OPENCLI_PROFILE_NAME=profile-A \
  -v opencli-hub-poc-data:/var/lib/opencli \
  opencli-hub:poc poc-entrypoint.sh
```

The production image now defaults to `hub-entrypoint.sh`; append `poc-entrypoint.sh` explicitly only for the retained F1 diagnostic stack.

This was verified to produce a connected extension and non-empty `contextId`
without adding `--no-sandbox` to Chrome.

For diagnosis only, the entrypoint accepts an explicit
`OPENCLI_REQUIRE_NO_SANDBOX=1`. It is off by default and must not be the
production deployment default.

## 7. Context identity verification

Measured results:

```text
Same Profile before restart: x2t98czs
Same Profile after restart:  x2t98czs
Different Profile:           t94hddym
```

Therefore:

```text
same persisted Chrome Profile -> same contextId
different Chrome Profile      -> different contextId
```

The entrypoint removes only stale Chrome process singleton links before startup:

```text
SingletonLock
SingletonSocket
SingletonCookie
```

This is required after an ungraceful container stop. It is safe because each
Profile is exclusively owned by one Hub Instance; persistent browser data,
cookies, extension storage and login state are not deleted.

## 10. Remaining production work

F1 proves feasibility; M4/I0 still need to integrate it into the Hub lifecycle:

1. assign a separate Profile directory, DISPLAY and VNC port per Instance;
2. run one shared OpenCLI daemon for all Instances;
3. discover newly connected `contextId` values by daemon profile-set difference;
4. preserve the fixed extension signing identity across image releases;
5. replace `seccomp=unconfined` with the narrowest tested seccomp allowance if
   the deployment security baseline requires it;
6. expose VNC only through the Hub WebSocket proxy;
7. retain `--shm-size=2g` or equivalent shared-memory capacity.
